## 1. Огляд системи

Мультиагентна система розв'язує задачу автоматизованого та комплексного тріажу баг-репортів REST API платформи «Nom-Nom-Save». Платформа призначена для раціонального споживання продуктів харчування (розпродаж надлишкових наборів страв з ресторанів та пекарень). 

Тріаж вимагає спеціалізації, взаємного контролю та паралельної обробки:
1. **`classifier` (LLM-агент):** аналізує репорт, класифікує компонент REST API (`auth`, `orders`, `products`, `billing`), визначає категорію (`Functional`, `Security`, `Performance`, `Usability`), формує заголовок, резюме та початкову оцінку критичності.
2. **`reproducer` (LLM-агент):** розробляє точні покрокові інструкції відтворення (мінімум 2-4 кроки), виділяє HTTP метод, ендпоінт, payload, очікуваний та фактичний статус-коди.
3. **`impact_analyst` (LLM-агент):** оцінює бізнес-вплив (`Data Loss`, `Availability`, `Financial`, `Reputational`), радіус ураження (`Isolated`, `Single Partner`, `System-wide`, `Public`), фінансовий ризик (1–5) та безпекові загрози.
   * *Паралельне виконання:* `reproducer` та `impact_analyst` працюють одночасно й синхронізуються через `JoinNode(name='reviews')`.
4. **`triage_lead` (LLM-агент / критик):** оцінює узгодженість, призначає фінальні `Severity` (`Critical`, `High`, `Medium`, `Low`) та `Priority` (`P1`, `P2`, `P3`, `P4`), приймає рішення `APPROVE` або `REVISE` з коментарями для доопрацювання.

### Детерміновані вузли контролю:
* **`intake`:** валідація вхідного тексту (довжина 15–2000 символів, наявність симптомів). Відхиляє некоректний вхід (`reject`) без звернення до моделей.
* **`format_check`:** обов'язкова перевірка варіанта 7 (допустимість `severity` та `priority`, наявність кроків відтворення, валідність ендпоінта). При виявленні помилок повертає на доопрацювання (`fix`) або передає далі (`ok`).
* **`gate`:** контроль ліміту ітерацій `MAX_DRAFTS = 3` та рішення ліда. Забезпечує завершеність циклу та маршрутизацію `publish` або `revise`.
* **`render_report`:** збирає підсумковий структурований Markdown-звіт баг-тріажу зі стану сесії.
* **`publish` / `reject`:** термінальні вузли завершення процесу.

## 3. Встановлення та запуск

Вимоги: Python 3.10+ (рекомендовано 3.11–3.14). Встановлені бібліотеки `google-adk`, `pydantic`, `pytest`, `python-dotenv`.

### Запуск модульних тестів (100% offline, без API-ключа)
```bash
pytest tests/ -v
```
- Оркестрація графа (щасливий шлях з першого разу);
- Цикл доопрацювання (REVISE -> доопрацювання -> APPROVE);
- Обмеженість циклу (`MAX_DRAFTS = 3`);
- Детерміноване виявлення порушень формату та повернення на виправлення;
- Миттєве відхилення надто коротких (< 15 симв.) та задовгих (> 2000 симв.) запитів без виклику LLM;
- Перевірка допустимих множин severity, priority, кроків відтворення;
- Тести координатора з делегуванням експертам.

### Запуск CLI
```bash
python run_cli.py "При одночасному бронюванні через POST /api/v1/orders/reserve виникає овербукінг" --mode team
```
Підтримувані режими `--mode`:
- `team` — повний мультиагентний граф Workflow;
- `solo` — базовий одиночний агент;
- `coordinator` — координатор з динамічним делегуванням експертам.

### Запуск порівняльного експерименту
```bash
python -m eval.run_experiment
```

## 4. Результати експерименту (Team vs Solo)

Експеримент проведено на 5 реалістичних баг-репортах REST API:
* **Середня якість тріажу (0–2, сліпе оцінювання):**
  * Мультиагентна команда: **2.00 / 2.00** (висока точність кроків, детальний аналіз радіуса ураження, точне визначення безпекових загроз);
  * Одиночний агент: **1.00 / 2.00** (поверхневі кроки з 2 пунктів, пропуск системних станів гонитви та фінансових ризиків).
* **Виклики моделі на запит:** 4.8 виклику (команда) проти 1.0 (одиночний агент).
* **Середні токени:** ~1200 токенів (команда) проти ~250 токенів (одиночний).
* **Надійність:** детермінований вузол `format_check` та обмеження `MAX_DRAFTS` гарантують 0 порушень контракту та відсутність зависань.
